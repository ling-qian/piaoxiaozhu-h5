两个设计取舍

  • 提示词通用化：H5 的提示词写死了「餐饮行业财务顾问」，这里改成「小微商户财务顾问」，并把六维分析结构保留下来（利润健康度 / 成本结构 / 趋势 / 商户集中度 / 建议 / 风险）。

HTTP 200，总耗时 16.8 秒，返回 1040 字分析。内容质量可接受——它准确识别出这批是测试数据 （零收入、纯支出、单一分类、商户名全是「某某餐饮管理有限公司第 N 分店」、单价统一 128.50）， 并给出「数据核查 → 科目重分类 → 关联采购审计 → 现金流止损」这类可执行建议，而不是泛泛而谈。

3. 记录搜索 / 筛选（本次新增）

为什么必须做在后端

记录列表是服务端分页（每次 20 条）。如果在前端过滤，用户只会看到「当前已加载那 20 条里匹配的」，看起来像数据丢了。所以筛选条件下推到 SQL。

参数行为
keywordILIKE 同时匹配商户名与一级分类——搜「京东」、搜「房租」都能命中
category_l1精确匹配一级分类名（用户看到的那个分类）
direction原有能力：in / out
避坑：分类筛选用 category_l1，不要用 category_code。 stats 接口里的 category_code 是从 category_l1 经映射表派生出来的，与原始记录里的值可能对不上。 （另外 cost_by_category[].category_l2 实际存的是一级分类名，字段名有误导性，但不是 bug。）

前端交互

  • 搜索框 400ms 防抖，不会每敲一个字打一次接口
  • 收支 chips：全部 / 支出 / 收入；分类 chips 可横向滑动
  • 筛选生效时显示「筛选结果 N 条」；结果为空时提示「没有符合条件的记录」并给出「清除筛选条件」
  • 实现细节：applyFilter() 把筛选值显式传给加载函数，而不是让它读 state——setState 是异步的，刚改完筛选立刻请求会拿到旧值

验证：接口 total 与 SQL 直查逐一比对

这组对比的意义是证明「筛选真的下推到了数据库」，而不是前端假过滤。

4. 两个比功能本身更要紧的发现

① 配置里的大模型已经下线，票据分类的 LLM 兜底一直在静默失败

第一次调用 AI 分析直接返回 503 model_not_found: agnes-2.0-flash。查服务商 /models 发现 2.0 系列已下架，现役是 2.5 / 3.0 系列。

影响面不止新功能。票据分类的 LLM 兜底（LLMClassifier）用的是同一个 LLM_MODEL_NAME， 所以它一直在失败并回落到关键词规则——这正是部分票据被归到「其他」的原因之一。

已实测改用 agnes-3.0-flash（1.8s 正常响应），并同步更新 services/api/.env 与 v1/.env.example。

部署云托管时，环境变量 LLM_MODEL_NAME 也要用新名字，别照抄旧值；否则线上会继续静默失败。

② 生成耗时决定了这个功能不能走云调用

实测（agnes-3.0-flash）：

max_tokens耗时输出结论
60013.4s965 字可用，但接近云调用上限
100021.2s880 字云调用必超时
2000>30s（被截断）不可行

据此把参数定为 max_tokens=900、超时 45s、提示词要求 600–800 字。

架构限制：微信云调用 callContainer 的超时上限是 15 秒。 这个接口同步走云调用会踩线甚至超时。若最终走 CallContainer 内测，本功能需改成 「入队 + 轮询」异步模式（像 OCR 那样），或让该接口单独走公网域名（云托管 request 上限 60s）。
