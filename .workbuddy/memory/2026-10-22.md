## 小票明细行加总 vs 合计 的交叉校验

新增 `packages/core/piaoxiaozhu_core/receipt_lines.py`，接入 `ocr_service`（仅小票场景）。

**原理**：小票没有税额可校验，但有明细行。把行尾金额加总与合计比对，
能抓出「合计读错」（如 19.30 → 193.00）这类规则层查不出的错误。

**解析规则**：取每行**行尾金额**（明细行几乎都以金额结尾）；排除含
合计/实收/找零/优惠/税额/税号/电话/地址等关键词的行；支持「15 x 12.00 180.00」
的 数量×单价 形态（若行尾金额≈数量×单价则用它，否则保留行尾金额）。

**防误报的四道闸**：
1. 明细 < 2 行不判断（漏识别一行时金额仍是对的，报警只是噪音）
2. 文本含 优惠/折扣/满减/抹零/减免/抵用/券 → 直接跳过（口径不一致）
3. 容差 max(0.5 元, 合计×1%)，覆盖四舍五入与抹零
4. 只有差异 > max(5 元, 合计×5%) 才报警

**验证**（6 个场景 + 7 条单测）：
| 场景 | 结果 |
|---|---|
| 正常小票 12.80+6.50=19.30 | 通过 |
| 合计读错 193.00 | **报警**（差 ¥173.70） |
| 数量×单价 180.00/32.00 | 通过（未把 15/12.00 当金额） |
| 有优惠 | 跳过 |
| 只有 1 行 | 跳过 |
| 抹零差 0.10 | 通过（容差内） |

**又踩一坑**：`_to_float` 未定义就用了，且外面包了 try/except → 会**静默跳过**整条校验
（只留一条 warning），比崩溃更隐蔽。已补 `_to_float`（处理 ¥/千分位/None，6/6 通过），
并用 7 条单测覆盖分支，防止再次静默失效。

**测试**：core 69 passed、后端回归 15/15、边界 29/29。后端包 225K 已更新到桌面。

### 验证方法坑：产物字符串探针的假阴性

Taro/webpack 产物把中文转义成 `\uXXXX`，但**只转义非 ASCII 字符**：
- 全角逗号 `，`(U+FF0C) 转成 `\uff0c`，而只转 `[\u4e00-\u9fa5]` 的探针会漏掉它

## callContainer 改造：修掉两个会导致全站不可用的 bug

用户说「马上修」，我先**验证再修**（用源码抽取 + node 执行的方式测真实代码文本）：

**验证 1：appendQuery（GET 参数拼接）8/8 通过** —— 空值过滤、中文编码、已有 `?` 追加、
POST 不拼参数，全部正确。这项原本担心会「筛选失效但看起来正常」，实际没问题。

**验证 2：发现两个真 bug**（都会让 callContainer 完全不可用）：

### ① 缺 `X-WX-SERVICE` 头
callContainer 靠这个 header 决定路由到环境里的**哪个服务**。不传不会自动匹配到 `api`，
表现为 404 / 服务不存在。已补：`header: { ...header, 'X-WX-SERVICE': 'api' }`，
服务名走 `TARO_APP_CLOUD_SERVICE` 常量（默认 `api`）。

### ② 响应体可能是字符串
`request()` 直接读 `res.data.detail`，而云调用的 `res.data` 在某些 dataType 下是**原始字符串**。
不改的话：所有错误提示变成 undefined，前端只剩「请求失败」四个字，排查无线索。
已加 `normalizeBody()`：字符串且以 `{`/`[` 开头 → JSON.parse，失败原样返回。单测 7/7。

**另确认**：COS 直传仍走 `Taro.request`（PUT 到 myqcloud.com），**不走 callContainer**——
这是对的，图片必须走对象存储域名，云调用不支持 uploadFile 且请求体限 100K。

tsc 0 错误，已重新构建。

### ★ 抓到最隐蔽的跨语言坑：`\w` 的 Unicode 语义
Python 的 `\w` **Unicode 感知**（中文算「字」），JS 的 `\w` **只认 ASCII**。
照抄 `/^[\W\d]+$/`（旧代码判断「是否全为无意义字符」）会把「盒马鲜生 正佳店」
判成无意义而跳过 → **中文商户名全军覆没**，且不报错，只是静默返回 null。
修法：`/^[^\p{L}_]+$/u` 精确复刻 `[\W\d]` 语义（= 除字母与下划线外的全部）。
对拍直接抓出（8/10 → 修后 10/10）。

### 其它保持一致的细节

## Worker 重写第六步：微信支付 V3（4,586 行 / 29 文件 / 25 路由）

### 加密能力（`lib/wechat-pay.ts`）
Workers 里没有 cryptography，全部 Web Crypto 实现：
- 商户私钥 PEM → **剥头尾 + base64 → DER → importKey("pkcs8")**
- 平台证书（X.509）→ **手写 DER 解析提取 SPKI**：
  搜索 rsaEncryption 的 AlgorithmIdentifier（`30 0D 06 09 2A 86 48 86 F7 0D 01 01 01 05 00`），
  往前找 SEQUENCE 头并按 DER 长度切片。也支持微信「公钥模式」的 PUBLIC KEY PEM（更简单，推荐）
- 回调 AES-256-GCM 解密；APIv3 密钥必须 32 字节（先校验长度，报错比解密失败的乱码好排查）

### 支付路由（`routes/payments.ts`）
- `POST /payments/wechat/prepay`：**金额一律服务端算**（套餐价 × 周期折扣 1/3/12 = 1.0/0.9/0.8，
  积分包独立定价），先落 pending 订单再下单，下单失败把订单标 failed 避免死单
- `GET /orders/:id`：以回调为准，不信前端 success
- `POST /payments/wechat/notify`：**验签 → 时间戳容差 300s → 解密 → 金额核对 → 幂等 → 发货**
  - 在**鉴权白名单**内（微信服务器不带 JWT），安全边界完全由验签承担
  - 幂等：已 paid 直接返回成功（微信会重推）
  - 金额不一致只记日志不发货
- `GET /plans`：价目表下发给前端，避免价格写死在两端
