## 商户名显示成「（章）」——OCR 提取 bug，已修并回归验证

**现象**：票据记录里商户名显示「（章」，用户误以为「显示不全」。
**实证**：库里该记录 `merchant_name='（章'`——**数据本身就是错的，不是显示问题**。

**根因（从 OCR 原文定位）**：原文末尾是
```
销售方
名
称：京东大药房（广州）有限公司      ← 正确值，但被 OCR 拆成三行
...
销售方：（章                        ← 盖章行
发票专用章
```
`_SELLER_LABEL_PATTERNS` 里的 `销售方[：:]\s*(.+?)` **命中了盖章行**，把「（章」当商户名返回；
而正确的「销售方\n名\n称：」因为中间隔着换行，`销售方[：:]` 匹配不到。

**修复（`packages/core/piaoxiaozhu_core/field_extractor.py`，3 处）**
1. 新增 `_SELLER_SPLIT_PATTERN = 销售方\s*名\s*称\s*[：:]\s*([^\n]+)`，**容忍换行**，优先级排在所有模式之前
2. 新增 `_is_seal_noise()`：命中盖章碎片（`（章`/`发票专用章`/纯括号包章）时**不再直接返回**，继续往后找
3. 兜底「逐行挑商户名」也加章过滤，并**先剥行首标签再判章**（顺序反了会漏掉 `销售方：（发票专用章）` 整行）

**验证**
- 边界用例 6/6 通过（换行拆分 / 单行 / 只有盖章行 / 商户名含「章」字不误杀 / 整行括号章 / 带标签前缀）
- **全量 A/B（318 条真实票据）**：新旧一致 317、新版更好 1、**潜在回归 0**
- 数据修复：43 条疑似坏数据中可靠修复 1 条（`'（章'` → `'京东大药房（广州）有限公司'`，已 UPDATE）；
  其余 42 条是测试数据（金额 1.00/1.05、商户名 m0~m4、空），新逻辑也提不出有效值，**未动**（保守原则）

## ⚠️ 方法论教训：回归验证必须「同输入 A/B」，不能拿新输出对比旧存量值

第一版回归我直接比「新代码输出 vs 库里已存 merchant_name」，得出 **300 条被改坏**的假结论，
差点回滚一个正确的修复。真相：那些记录的商户名来自 **LLM 分类或手工录入**，根本不经过
`field_extractor` 这条正则路径，两边不可比。
**正确做法**：用 git/反向编辑重建「改前版本」，对同一批输入跑新旧两个 `extract_fields` 再对比。
⇒ 以后凡是要证明「我的改动没弄坏别的东西」，一律做同输入 A/B；单侧对比（新 vs 存量）会得出假回归。

## 头像加载失败「Failed to load image .../__pageframe__/files/static/...」——相对路径 bug，已修

**报错含义**：小程序 `<Image>` 加载图片失败。URL 里的 `127.0.0.1:<端口>/__pageframe__/` 是**微信开发者工具**的预览代理前缀，说明图片请求根本没到我们后端。

**根因**：未配置对象存储时，后端 `storage.py:local_public_url()` 返回的是**相对路径** `/files/static/avatars/...`；
而小程序 `<Image>` 把以 `/` 开头的地址当作**本地包内资源**（不是网络地址），于是永远找不到文件。
⇒ **这是个隐性 bug**：配了 OSS/COS 时后端返回绝对地址，一切正常；只有本地存储（或任何没配对象存储的环境）才会暴露。

**修复**：
- `apps/miniapp/src/services/api.ts` 新增导出 `resolveMediaUrl(url)`：`http(s)://` 原样返回；`/` 开头则拼上 `BASE_URL`（即编译进来的 `TARO_APP_API_URL`）；其他（`http://tmp/...`、`wxfile://...`）原样返回
- 两个渲染点接上：`pages/mine/index.tsx:153`（我的页头像）、`pages/profile/index.tsx:99`（编辑资料页头像）
- `pages/upload/index.tsx:338` 的 `task.filePath` 是 chooseImage 的本地临时路径，**不受影响**；票据图片 UI 里没有展示点，无需改

**验证**：`tsc --noEmit` src 0 错误；`resolveMediaUrl` 单测 5/5（相对路径/COS 绝对地址/chooseAvatar 临时路径/wxfile/空值）；
**端到端**：用报错里那个真实头像路径直接打后端 → `HTTP 200 / 4568 bytes / image/jpeg / 132×132`，证明补全后的地址确实能取到图。
已 grep 确认无遗漏的渲染点（profile 里剩下的 `avatar_url` 引用都是 state 赋值，最终都走到 line 99 的 resolveMediaUrl）。

**可复用规则**：以后任何「后端返回的媒体地址」渲染前都必须过 `resolveMediaUrl`；新增展示票据图片等功能时直接用它，别再用裸字段。

### 对照官方文档核对 `getuserphonenumber` 的两处补强

## 小程序 vs H5 功能差异（用户要求「把 h5 上的功能都添加到小程序上」）

**实测对照结论**（H5 = `piaoxiaozhu-h5`，Next.js + Prisma + **Stripe**；小程序 = `v1/apps/miniapp`）
- H5 独有路由：`analysis`（AI 经营分析）、`promo`（营销落地页）、`admin/upgrade`（管理端）、`auth`（邮箱密码登录）
- **真正的功能缺口只有 2 个**：
  1. **AI 经营分析**（H5 `/analysis`：收入/支出/毛利汇总 + 月度趋势 + 分类占比 + AI 文字结论）→ 本轮已实现
  2. **记录搜索/筛选**（H5 report 页有）→ 小程序没有，待定
- **平台不适用**（不是缺口）：Stripe 支付（小程序用微信支付）、`auth` 邮箱密码登录（小程序用微信登录）、
  `admin`（管理端）、`sw-registrar`（Service Worker，Web 独有）、`promo` 营销落地页（小程序内无落地场景）
- 两边都有：报表、CSV 导出、分享、会员套餐、工具包、隐私政策

## 方案 A：手机号成为账号第二身份（已实施后端）

**决策背景**：用户希望「登录注册像大众点评」，并明确「需要用户信息做后续用户分析」。
- 核对官方文档后确认：**「一次性弹窗同时拿头像+昵称」已不存在**（2022-10 收回 getUserProfile）；
  头像只能 `button open-type=chooseAvatar`，昵称只能 `input type=nickname`。

- **根本差异**：大众点评是「手机号=账号主体 + 有登录墙」；我们是「openid 账号主体 + 无感登录」。
  改成登录墙有审核风险（强制收集个人信息）且流失高 ⇒ 选择方案 A：**升级账号体系，不加登录墙**。

   已 apply 到库：`CREATE UNIQUE INDEX ix_users_phone`；`alembic check` 无待生成变更。

3. `bind-phone` 增加**冲突检查**：该手机号已属其他账号 → **409**「已绑定其他账号，如需合并数据请联系客服」。
   （此前是直接 `current_user.phone = phone` 覆盖，配合非唯一索引会造出同号多账号。）
4. 新增 **`POST /api/auth/wechat/phone-login`**：code → 手机号 → 按手机号定位账号 → 签发 token；
   找不到 → 404「该手机号还没有绑定过账号」。
5. 前端 `mine` 页：未绑定手机号时显示引导条「绑定手机号 / 换手机或换微信后可用手机号找回账号」→ 跳 profile 页。

## 边界条件体检（29 条用例）——抓到并修掉 2 个真 bug

**脚本**：`v1/infra/edge_cases.py`（固化，跑法见文件头；会自动建临时用户+项目、结束级联删除）。

**修复 1 · 搜索关键词的 ILIKE 通配符未转义（真实缺陷）**
用户输入 `%` 或 `_` 会被拼成 `ILIKE '%%%'` / `'%_%'`，**匹配全部记录**（实测 300/300），
表现为「搜索没生效」。已在 `records.list_records` 里转义 `\ % _` 并显式传 `escape="\\"`；
修复后输入 `%` / `_` 均返回 0 条。

**修复 2 · 免费套餐可以下单（真实缺陷）**
`prepay` 只校验 plan 存在，free 的 `price_cents=0` 也能建单 → 生成 0 元 pending 订单，
走到支付网关必然失败。已加 `plan.price_cents <= 0 → 400「免费套餐无需购买」`；并清理了测试产生的 0 元订单。

**通过的关键临界项**
- **并发双花**：余额只够一次时两个并发 `consume` → 成功 1/2、最终余额 0 ⇒ `SELECT users FOR UPDATE` 生效。
- 余额恰好等于成本 → 允许且归零；余额 0 再扣 → 抛 `InsufficientPoints`；扣 0 / 发负数 → 抛 `ValueError`。

- 分页：页码越界 → `items=[]` 但 total 正确；`size=101` → 422。
- 鉴权：无 token / 伪造签名 / 过期 token → 均 401。
- 越权与非法 id：他人项目、非 UUID、随机 UUID → 均 404（不是 500）。

没数据可分析就不该收费，顺序正确。回归脚本原先随便选项目导致误报，已改为只选「带记录的项目」。

## deploy.sh 接入部署后自检

## ★ 小程序构建配方（第 7 次尝试成功，之前全败）

**根因**：Taro 对已存在的 `dist` 会再调一次**不带 recursive 的 mkdir**，被本机 node fs 沙箱
（brokered-fs shim）判为 host-op 拒绝 → `CODEBUDDY_BROKER_DENY / EEXIST`，整个构建崩在最后写盘阶段。

**失败的三种加载顺序（都试过）**
1. `NODE_OPTIONS=--require=patch.cjs` 只打补丁、不先加载 shim → 补丁被宿主**随后注入的 shim 覆盖**；
2. 补丁写在 `config/index.ts`（构建期才加载）→ 覆盖了同步版/promises 版仍失败，因为调用方
   （mkdirp / webpack 输出）用的是**回调版 `fs.mkdir`**，且可能在 config 加载前就捕获了引用；
3. 单独任一种都不够。

**可用配方（三件事必须同时做）**
```js
// /tmp/force-mkdir2.cjs
require('<WorkBuddy>/app.asar.unpacked/cli/vendor/shim/node-brokered-fs-shim.cjs');  // ① 先加载 shim
const fs = require('fs');                                                            // ② 再打补丁
const force = o => (o === undefined ? {recursive:true}
  : (typeof o === 'object' && o) ? {...o, recursive:true} : o);
fs.mkdirSync = (p,o) => rawSync.call(fs, p, force(o));                                // ③ 三种调用形式全覆盖
fs.promises.mkdir = (p,o) => rawP.call(fs.promises, p, force(o));
fs.mkdir = (p,o,cb) => { let c=cb; if (typeof o==='function') {c=o;o=undefined;} return rawCb.call(fs,p,force(o),c); };
```
```bash
cd v1/apps/miniapp && /bin/rm -rf dist \
  && NODE_OPTIONS="--require=/tmp/force-mkdir2.cjs" npm run build:weapp
```
成功标志：`webpack 5.90.0 compiled successfully` + `EXIT_CODE=0` + dist 有 19 个文件（约 325 秒）。

**产物验证方法（Taro 3 的特性，别再查错地方）**
- wxml 是 `v-root` 模板，**类名不在 wxml 里**，要在 `dist/pages/<page>/index.js` 里 grep 类名；
- 中文文案在产物里是 `\uXXXX` 转义，**不能直接 grep 中文**；
- 可靠判据：`dist/app.json` 的 `pages` 数量、`dist/app.js` 的 mtime、包内后端地址
  （`grep -ohE 'http://[0-9.]+:[0-9]+' dist/*.js`）。

**本轮成果**：dist 已于 10-19 19:49 重建——12 个页面（含 analysis、points）、
5 个新组件类名（points-card / checkin-pill / quick-grid / period-chip / filter-bar）全部在包、
4 个积分接口（/api/points、/checkin、/logs、/packages）全部接线、包内地址 172.16.20.37:8000。
临时补丁已从 config/index.ts 撤掉（仓库干净），但 preflight 会因此误报一次
「config/index.ts 比 dist 新」——下次构建后自然消失。

**重大发现（决定支付能否免备案）**：微信云托管有**官方封装支付**
（`developers.weixin.qq.com/miniprogram/dev/wxcloudservice/wxcloudrun/src/guide/weixin/pay.html`）：
- 云托管扮演「微信支付服务商」，商户号填 `sub_mch_id`、AppID 填 `sub_appid`，**免填 mch_id/sign/sign_type**
- **私有安全链路、免证书管理**
- **回调走内网**：统一下单参数里传 `env_id` + `callback_type: 2` + `container:{service, path}`，
  支付结果直接推到指定云托管服务的内部路径；服务必须返回 `{"errcode": 0}`
- 接口：`POST http://api.weixin.qq.com/_/pay/unifiedOrder`（走「开放接口服务」开关），返回 `payment` 字段可直接给 `requestPayment`
- ⇒ **这条路完全不需要公网域名/备案**，是绕开备案上支付的唯一可行路径
- 开通：申请商户号 → 关联到小程序 AppID → 云托管控制台「设置→其他设置→微信支付配置」绑定 → 商户号超管确认 → 在商户平台确认 jsapi/退款权限
- ⚠️ 待验证：开启「开放接口服务」会改变云托管内对微信 API 的调用方式（文档说开启后默认走云调用），
