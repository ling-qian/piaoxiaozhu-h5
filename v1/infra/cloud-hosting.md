# 票小助 Pro · 微信云托管部署手册

> 目标：把 `v1` 的 FastAPI 后端部署到微信云托管，让小程序（体验版/正式版）能真机联网。
>
> ⚠️ **先读第 10 节「备案与域名」**。一个容易搞错的前提：云托管的**默认公网域名不能被配置到
> 小程序后台**（官方明确「仅能支持接口测试，请勿用于正式生产」），所以「走公网调用」这条路
> 必须有自己的**已 ICP 备案域名**；完全免备案的通道只有云调用 CallContainer，而它撑不起票据
> 图片上传。这个坑在本仓库早先的 `cloudrun-migration-assessment/` 评估里已经查证过，结论一致。
>
> 本文只覆盖后端部署。小程序端的提审配置见 `docs/launch-readiness.html`。

---

## 1. 目标架构

```
小程序（Taro）
   │ HTTPS
   ▼
┌───────────────── 微信云托管环境 ─────────────────┐
│  api 服务（FastAPI）      worker 服务（Celery）  │
│  不含 OCR 依赖            含 PaddleOCR + 模型    │
│  约 300MB                 约 2GB+               │
└───────┬─────────────────────────┬──────────────┘
        │                         │
        ▼                         ▼
  腾讯云 PostgreSQL          腾讯云 Redis
        │
        ▼
  对象存储（腾讯云 COS 或阿里云 OSS）
```

要点：
- **api 与 worker 镜像分开**。OCR 依赖是懒加载的，api 只在 Celery 不可用时才会用同步兜底，
  因此 api 镜像可以不带 paddle 系依赖，冷启动与内存规格都显著更好。
- worker 不监听 HTTP，创建服务时不要配端口。
- 两者共用同一个构建上下文 `v1/`（因为要装 `packages/core` 共享包）。

## 2. 服务清单与配置

在云托管控制台创建 **1 个环境**，里面建 **2 个服务**。

### 2.1 api

| 配置项 | 值 |
|---|---|
| 构建方式 | 代码仓库 / 代码包上传（二选一，见 §3） |
| 构建目录 | `v1`（仓库里的 v1 目录） |
| Dockerfile 路径 | `services/api/Dockerfile.api` |
| 服务端口 | `8000`（填 80 也行，启动脚本会读 `PORT` 自适应） |
| 实例规格 | 0.5 核 1GiB 起（起步阶段够用） |
| 最小副本 | **api = 1**，**worker = 1（不能设 0，见下方警示）** | 见 §7 的扩缩容说明 |
| 健康检查 | 路径 `/health`（已实现，返回 `{"status":"ok"}`） |
| 实例数量 | 1 |

### 2.2 worker

| 配置项 | 值 |
|---|---|
| 构建目录 | `v1` |
| Dockerfile 路径 | `services/api/Dockerfile.worker` |
| 服务端口 | **不配**（后台服务） |
| 实例规格 | **2 核 4GiB 起**（PaddleOCR CPU 推理很吃内存，1GiB 会被 OOM Kill） |
| 实例数量 | 1（要吞吐时加副本，不要加容器内并发） |

### 2.3 环境变量

按 `infra/cloud-hosting.env.example` 逐条填，两个服务**各填一份**。
文件里已标注每个变量属于 `[两者]` / `[仅 api]` / `[仅 worker]`。

### 2.4 数据库与 Redis

数据库用 **PostgreSQL**。两种部署形态，按阶段选：

| 阶段 | 方案 | 月成本 | 说明 |
|---|---|---|---|
| **内测 / 开发** | **Neon（新加坡）** | ¥0（免费层） | 免运维、按量、自动挂起。延迟约 50–80ms，可接受 |
| **正式上线** | 腾讯云 PostgreSQL（与云托管同 VPC） | ~¥70–240 | 延迟 1ms、数据在境内，合规更稳 |

#### 方案 A：Neon（当前使用）

1. 在 https://neon.tech 建项目，**Region 选 Singapore（ap-southeast-1）**。
2. 复制 **Pooled connection** 串（主机名带 `-pooler`），加驱动前缀：

   ```
   DATABASE_URL=postgresql+asyncpg://<user>:<pass>@ep-xxx-pooler.ap-southeast-1.aws.neon.tech/<db>?sslmode=require
   ```

3. **必须注意**：Neon 的 pooler 是 PgBouncer（transaction 模式），**不支持服务端预编译语句**。
   并发稍高时 asyncpg 会报 `prepared statement "__asyncpg_stmt_1__" already exists`。
   `app/models/database.py` 检测到 `neon.tech` 会自动关闭 statement cache 并把连接池收小，
   **不需要额外配置**，但**不要**手动把 `pool_size` 调大。
4. 免费层 5 分钟无访问会挂起，下次查询自动唤醒（约 1–2 秒）。失败重试由 `pool_pre_ping` 兜住。
5. 免费层**没有长期备份**，只有 6 小时恢复窗口。数据有价值后要定期 `pg_dump`。

#### 方案 B：腾讯云 PostgreSQL（上线后建议切回）

1. 在腾讯云控制台创建 PostgreSQL 实例，**与云托管环境同一个 VPC**
   （官方 FAQ：「使用其他数据库可以自行到腾讯云上购买，搭配云托管使用，买在和云托管
   同一个 VPC 下即可」；VPC 路径：控制台 → 设置 → 环境设置 → 网络）。
2. 建库（如 `piaoxiaozhu`）与账号。
3. 内网连接串：

   ```
   DATABASE_URL=postgresql+asyncpg://piaoxiaozhu:<密码>@10.x.x.x:5432/piaoxiaozhu
   ```

   不在同一 VPC 时需配内网互通；实在不行只能走公网 + SSL（URL 追加 `?ssl=require`），
   延迟与流量费都会明显上升。

#### 从 Neon 迁到腾讯云 PG

两边都是 PostgreSQL，数据量小（图片在 COS，不占库）：

```bash
pg_dump "<neon连接串>" --no-owner --no-acl -f /tmp/pzx.sql
psql "<腾讯云连接串>" -f /tmp/pzx.sql
```

迁完只改云托管环境变量里的 `DATABASE_URL`，重启服务即可，**代码零改动**。

#### Redis

用云托管提供的 Redis，或腾讯云 Redis 实例；把地址填进 `REDIS_URL`。

> 若采用「OCR 同步模式」内测（见 §7 成本说明），可暂不部署 worker 与 Redis。

> 迁移不要依赖 `app` 启动时的 `create_all` 去打天下：它只建表不改造，
> 且已有库不会被它改动。首次部署请按 §5 跑一次 `alembic upgrade head`。

## 3. 构建上下文为什么必须是 v1/

原来 `services/api/Dockerfile` 有两个问题，已在本轮修掉：

1. `requirements.txt` 里写了裸包名 `piaoxiaozhu-core`。这个包不在 PyPI 上
   （它是仓库里的 `packages/core`），且原来的构建上下文只有 `services/api`，
   拿不到它 ⇒ `pip install` 必然报 `No matching distribution found`。
2. 单个镜像里塞了 api + worker 两套依赖。

现在改为：**构建上下文 = `v1/`**，Dockerfile 里显式 `pip install ./packages/core`。
同时新增 `v1/.dockerignore` 排除 `node_modules` / `venv` / `venv2` / `uploads` /
`.env` / `*.pem`——**这一步不能省**，否则构建上下文是 1.5GB（含 485MB 的
`apps/miniapp/node_modules` 和 1GB 的 `services/`），上传会慢到不可用。

构建方式三选一：

- **手动上传代码包（最快，已实测）**：云托管「新建版本 → 上传代码包」只收 **≤2MiB** 的 zip。
  实测下面这条命令打出来的包是 **0.39 MiB**（204 个文件），可以直接传：
  ```bash
  cd v1
  zip -rq /tmp/v1-codebundle.zip . \
    -x "*/node_modules/*" "*/dist/*" "*/venv/*" "*/venv2/*" "*/uploads/*" \
       "*.pyc" "*__pycache__*" ".env" "**/.env" "*/.swc/*" "*/.vercel/*"
  ```
  上传时的高级配置：目标目录不填（即包根目录）、**Dockerfile 路径填 `services/api/Dockerfile.api`**
  （worker 服务填 `services/api/Dockerfile.worker`）、端口 8000（worker 不配端口）。
  已验证包内**不含** `.env` / `*.pem` / `*.key`，也不含 node_modules、venv、上传数据。
  ⚠️ `.swc`（Taro/SWC 缓存，单个 2.6MB）**必须排除**，否则白白占掉大半额度。
- **代码仓库**：把仓库连到云托管，构建目录填 `v1`，Dockerfile 填上面的路径。
- **本地构建后推镜像**：本机执行（注意上下文是 `v1`，不是 `services/api`）

  ```bash
  cd v1
  docker build -f services/api/Dockerfile.api    -t <你的镜像仓库>/piaoxiaozhu-api:latest .
  docker build -f services/api/Dockerfile.worker -t <你的镜像仓库>/piaoxiaozhu-worker:latest .
  ```

本地起全套（含 PG/Redis）验证：

```bash
cd v1/infra
docker compose up -d
docker compose exec api alembic upgrade head
curl -s localhost:8000/health
```

### 一条命令做完整自检

```bash
cd v1
bash infra/preflight.sh                    # 只做静态检查（快，无需 Docker / 无需后端）
bash infra/preflight.sh --with-api         # 额外跑后端回归冒烟(15条) + 边界体检(29条)
bash infra/preflight.sh --build            # 额外真实构建两个镜像
bash infra/preflight.sh --with-api --build # 部署前的完整检查
```

它会检查：关键文件是否齐全、入口脚本是否可执行、**Dockerfile 里的 COPY 路径是否都在构建上下文内**、
`requirements` 有没有把本地共享包写成裸包名、`.dockerignore` 有没有漏掉 `node_modules/venv/uploads/.env`、
py_compile 与 `app.main` 能否导入、compose 结构、以及环境变量必填项。

`--with-api` 会调 `infra/regression_check.py` 与 `infra/edge_cases.py`，**要求后端已在 8000 运行**；
后端没起时会记 SKIP（不算失败）。注意边界体检会在库里建一个临时用户与项目，结束自动删除。

Docker CLI 不可用的环境可加 `PREFLIGHT_SKIP_DOCKER=1` 只跑静态部分。退出码非 0 表示有失败项。

## 4. 对象存储接入

`app/services/storage.py` 是统一的存储层，按下面顺序自动选择后端：

| 优先级 | 条件 | 行为 |
|---|---|---|
| 1 | 配了 `COS_*` | 走腾讯云 COS（与云托管同厂商，可内网，推荐） |
| 2 | 配了 `OSS_*` | 走阿里云 OSS（原方案，业务代码零改动） |
| 3 | 都没配 | 落容器本地盘（仅本地开发；**云托管重启即丢，生产必须配 1 或 2**） |

本轮顺带修了一个**会导致生产下 OCR 全线失败的 bug**：
`app/worker.py` 原来只从容器本地磁盘读图（`Path("uploads")/file_key`），
一旦启用了对象存储，worker 本地根本没有这个文件，于是每张票都被标记为
`ocr_status=failed`。现在改为统一走 `storage.download_object()`，
本地缓存未命中会自动回源远端。

接入步骤（以 COS 为例）：
1. 腾讯云创建 COS 存储桶（与云托管同地域），记下 `Bucket`（形如 `xxx-1250000000`）与 `Region`。
2. 创建子账号密钥（**不要用主账号密钥**），只授予该桶的读写权限。
3. 把 `COS_SECRET_ID / COS_SECRET_KEY / COS_REGION / COS_BUCKET_NAME` 填进 api 与 worker 的环境变量。
4. 验证：上传一张票 → 到 COS 控制台确认对象存在 → 首图能出识别结果。

> ⚠️ 说明：COS 这条分支是本次新写的，**未做真实联调**（本地无凭据）。
> 首次接入时请按上面第 4 步验证一次；阿里云 OSS 分支保持原有实现未动。

## 5. 首次部署步骤

> 迁移链本身已经在本机验证过：在一个**临时空库**上执行 `alembic upgrade head`，
> 四个迁移按序成功应用（`initial` → `make_file_id_nullable` → `add project_limit to plans`
> → `add subscription period fields`），建出 10 张表，并且 `alembic check` 返回
> `No new upgrade operations detected` —— 即**迁移与 ORM 模型完全一致**，生产库不会出现
> 「模型有字段、库里没有」的缺口。验证完临时库已删除，未触碰任何已有库。

1. 建 PostgreSQL 实例与库、建 Redis，拿到内网地址。
2. 云托管建环境 → 建 `api` 服务（按 §2.1 配置）→ 填环境变量 → 部署。
3. 改 `api` 服务环境变量，临时加 `RUN_MIGRATIONS=true`，触发一次重新部署，
   观察日志里 `alembic upgrade head` 执行成功（这一步建表）。
4. 把 `RUN_MIGRATIONS=true` 改回 `false`（避免多副本并发迁移）。
5. 建 `worker` 服务（按 §2.2）→ 填环境变量 → 部署。
6. **域名（关键，别按老经验来）**：云托管的默认公网域名**只能用于接口自测，不能配进小程序后台**。
   要让真机联网，两条路二选一，详见 §10：
   - **云调用 CallContainer**：小程序端改走 `wx.cloud.callContainer`，**无需域名、无需配置服务器
     域名、无需备案**；但它是 request 型接口，没有 uploadFile 等价物，图片上传要另做方案。
   - **自定义域名**：绑定一个**已 ICP 备案**的域名（+ HTTPS 证书 + CNAME），再配进小程序的
     request / uploadFile 合法域名。**正式发布走这条。**
7. 验证：`curl https://<你的域名>/health` 返回 `{"status":"ok",...}`。

### 迁移的三种跑法（任选）

- **投产前**：本地连生产库跑 `alembic upgrade head`（需临时把库地址开到本机）。
- **云托管任务**：用「任务」功能执行 `alembic upgrade head`，一次性、不占副本。
- **临时开关**：api 环境变量 `RUN_MIGRATIONS=true` 部署一次，跑完改回 `false`。

## 7. 规格、冷启动与成本

| 项 | 建议 | 原因 |
|---|---|---|
| api 规格 | 0.5–1 核 / 1GiB | 镜像小、无 OCR，纯 IO 与轻计算 |
| worker 规格 | 2 核 / 4GiB | PaddleOCR CPU 推理内存占用高 |
| worker 副本 | **1，且最小副本必须为 1（不能设 0）** | 见下方警示；先跑通，队列积压再加副本 |
| 最小副本 | api ≥1；**worker 必须 ≥1** | 见下方警示 |
| 镜像体积 | api ~300MB / worker ~2GB+ | worker 已把 OCR 模型预热进镜像，避免每次冷启动重下 |

> ### ⚠️ worker 最小副本绝不能设 0（官方明确说明，且后果比"冷启动"严重得多）
>
> 微信云托管官方《开发常识》扩缩容一节原文：
> 「自动扩缩容只根据 **HTTP 请求流量**判断，如果服务**不接受外部请求**，只是在自行跑任务，
> **会被「误判」为没有使用，触发缩容**。此种场景，请手动设定实例副本数最小值为 1，保持常驻。」
>
> 我们的 worker 正是「不接受 HTTP 请求、只跑 Celery 任务」的服务，完全命中这条：
> - 最小副本设 0 → 半小时无流量就被缩容到 0；
> - 而**扩容同样是由 HTTP 流量触发的**，worker 没有流量 ⇒ 可能永远不会被拉起；
> - 结果不是「首张票慢一点」，而是 **OCR 任务全部堆积在 Redis 里无人处理**。
>
> 另外 FAQ 也确认了常驻方法：「将最小实例副本数设置为 1 即可」
> （服务管理 → 服务列表 → 服务设置 → 基础信息）。
>
> ⇒ **worker 常驻是硬要求，成本约 174 元/月，必须计入预算**。
> 想省这笔钱只有一条路：砍掉 worker，让 api 同步跑 OCR（见 §12.4 方案 C）。

成本大头是 worker（常驻内存 + OCR 推理）。观测一周真实用量后再决定
是否加副本（而不是动最小副本数）。

## 8. 排障速查

| 现象 | 先看哪里 |
|---|---|
| 服务起来就退出 | api 启动日志里的 `配置体检未通过`：JWT_SECRET 是默认值 / DATABASE_URL 是 sqlite / 没有 LLM_API_KEY（`APP_ENV=production` 时会直接拒绝启动） |
| 登录报「登录服务暂未开放」 | `WX_APPID` / `WX_SECRET` 没配全 |
| 上传成功但一直没有识别结果 | worker 是否在跑；worker 日志里 Redis 地址是否正确；`invoice_files.ocr_status` 是 `processing` 还是 `failed` |
| worker 被反复重启 | 内存不足（OOM），升规格或把 `CELERY_CONCURRENCY` 压到 1 |
| 图片 404 / 打开是空白 | 对象存储没配全（`describe_backend()` 会打印当前生效后端，见启动日志）；或桶权限不是公共读 |
| 小程序请求报「不在合法域名列表」 | 域名没加到小程序后台 / 不是 HTTPS / **域名未备案**（微信会定期核查已配置域名的备案状态）；如果在服务器域名页「保存时」就被拒，基本就是备案没通过或主体不一致 |
| 上传代码包时报体积超限 | 代码包上限 **2MiB**；确认排除了 `node_modules` / `venv` / `dist` / `.swc`（Taro 缓存单个就 2.6MB）/ `uploads` |
| 支付相关接口返回 503 | `WX_MCH_ID / WX_API_KEY / WX_CERT_SERIAL_NO / WX_PRIVATE_KEY_PATH / WX_PLATFORM_CERT_PATH / WX_NOTIFY_URL` 有缺项，或启动日志里 `微信支付凭证校验未通过`（如 APIv3 密钥不是 32 字节、私钥/平台证书加载失败）。对照 §11 逐项核对 |
| 用户付了钱但没开通套餐 | 先看 api 日志有没有收到回调。收不到 = `WX_NOTIFY_URL` 没配进商户平台或域名不可达；收到但报「回调研验失败」= 平台证书配错（用了商户证书）或 `WX_API_KEY` 不对 |
| 生产启动即退出，提示未配置对象存储 | 这是有意为之：`APP_ENV=production` 且 `COS_* / OSS_*` 都没配。补齐对象存储后重启 |

## 10. 备案与域名（必读，直接决定上线时间表）

### 10.1 小程序备案：强制，个人主体也躲不掉

- 依据：工信部《关于开展移动互联网应用程序备案工作的通知》（2023-08-04）。微信公众平台
  自 **2023-09-01** 起执行：**未完成备案的小程序不能上架**；已上架的存量小程序须在
  2024-03-31 前补齐，逾期清退。
- **个人主体同样必须备案**，没有针对个人的豁免；个人主体备案数量上限为 **5 个**。
- 只有两种情形可暂不备案：① 境外主体；② **仅用于内部测试、不对外发布**的小程序。
  体验版内测可以落在第 ② 类，但**一旦要公开发布，就必须先完成备案**。
- 入口在小程序后台（设置 → 小程序备案），**全程免费**。材料：主体证件、负责人身份证、
  核验照片、服务器信息、服务内容标识。时效：平台初审 1–2 个工作日，管局 1–20 个工作日。
- 个人主体注意两点：**服务内容标识不能选经营性质 / 企业性质 / 涉及前置审批的类目**；
  小程序名称也不能带「公司 / 集团 / 商城 / 商贸」或「金融 / 财税 / 新闻 / 医疗」等前置审批
  关键词，否则备案入口会直接提示改名。这与前面「类目选工具、文案规避记账/财税」是同一条逻辑。
- 未备案就发布，微信返回 `errcode 86369 / 小程序上架需先完成备案`。

> 别混淆：**小程序备案 ≠ 网站 ICP 备案 ≠ ICP 经营许可证**。三者同属工信部体系但对象不同。
> 本项目只需要第一种（非营利性质，无需许可证）。已有同主体网站备案号可在小程序备案里复用，
> 但主体不一致不能借号。

### 10.2 域名 ICP 备案：取决于走哪条通道

| 通道 | 需要域名备案吗 | 说明 |
|---|---|---|
| 小程序 `wx.request` / `uploadFile` 直连公网 | **需要** | 微信要求这些合法域名已完成 ICP 备案，保存时会校验 |
| 云托管**默认公网域名** | —— | **不能用**。官方原文：「仅能支持接口测试，请勿用于正式生产环境。小程序后台也无法配置使用默认公网域名」 |
| 云托管 **CallContainer（云调用）** | **不需要** | 走微信私有协议内网链路，**无需域名、无需配置服务器域名、无需备案**；要求基础库 ≥ 2.23.0 |
| 云托管**自定义域名** | **需要** | 绑定已备案域名 + HTTPS 证书 + CNAME，正式发布走这条 |

### 10.3 对本项目的实际影响

CallContainer 是「request 型」接口，**没有 uploadFile 的等价物**，官方也明确
「请求中不建议包含图片，请通过对象存储处理」；再叠加云托管的运行时硬限制
（请求超时 60s、请求体 100KiB 文本 / 20MiB 二进制、返回体 ≤1000KiB），
**票据图片上传这一环很难只靠 CallContainer 撑起来**。

结论：
1. **小程序备案躲不掉**——它是上架门槛，与后端怎么部署无关。
2. **域名备案在「图片上传 + 正式发布」两点上同样很难绕开**；免备案的 CallContainer 更适合
   当作「先跑通非图片链路、尽快拿体验版反馈」的过渡手段，而不是终局方案。
3. **建议现在就把两件事并行启动**（都是纯等待项，不占开发工时）：小程序备案（免费，1–20 个
   工作日）；域名 ICP 备案（1–3 周）。否则它们会成为上线前唯一剩下的阻塞点。

> 含官方引用、成本测算与三方方案对照的完整论述见仓库里早先的
> `cloudrun-migration-assessment/cloudrun-migration-assessment.html`；本文只做结论收敛。

## 12. 采购清单与成本估算（有一个几乎人人都会漏的坑）

### 12.1 要不要额外买云服务？要。清单如下

| 项目 | 必须吗 | 参考价格 | 说明 |
|---|---|---|---|
| 微信云托管（容器） | **必须** | 见 §12.2 | 部署平台本身，按量付费 |
| 腾讯云 PostgreSQL | **必须** | 入门档约 60–150 元/月（以控制台为准） | 云托管一键只给 MySQL，我们**不做迁移**；需与云托管**同地域**才能走内网 |
| Redis（Celery broker） | **必须**（除非砍掉 worker，见 §12.4-B） | 入门档约 30–80 元/月 | 云托管官方明确「不支持用来部署数据库 / Redis 等有状态服务」，所以不能在云托管里起 Redis 容器 |
| 对象存储（票据图片） | **必须** | 云托管自带对象存储，或腾讯云 COS，约 1–5 元/月 | 图片不大，是零头；别用容器本地盘（重启即丢） |
| 域名 | 走公网才需要 | .cn ≈ 29 元/年，.com ≈ 70 元/年 | 只走 CallContainer 可完全不买 |
| 域名备案 | 走公网才需要 | 免费，但**见 §12.3 的坑** | 备案本身不收费，卡的是「备案服务号」 |
| 微信小程序认证 | 大概率不需要 | — | 我们无支付、无手机号组件；以控制台提示为准 |
| 小程序备案 | **必须**（上架门槛） | 免费 | 见 §10.1，与买不买云服务无关 |

### 12.2 云托管计费（官方定价，2026-10 核对）

| 项 | 刊例价 | 首个环境赠送（有效期 **3 个月**） |
|---|---|---|
| CPU | 0.055 元/(核·小时) | 720 核·小时 |
| 内存 | 0.032 元/(GB·小时) | 1440 GB·小时 |
| 构建时长 | 0.05 元/分钟 | 600 分钟 |
| 公网流量 | 0.8 元/GB | 5GB |

**⚠️ 「3 个月免费」是个容易误读的数字。** 按我们的配置（api 0.5 核 1G + worker 2 核 4G，均常驻）：
每天消耗 CPU ≈ 2.5×24 = **60 核·时**、内存 ≈ 5×24 = **120 GB·时**。
赠送额度只能覆盖 ≈ **12 天**（720/60 与 1440/120 都是 12 天）。
**所以预算要按「约两周后开始计费」来做，不是三个月。**

另外两点省钱信息：
- **走 CallContainer 不计公网流量**（走微信私有协议，不是公网出入口）。
- 构建时长按分钟计费：api 每次 3–5 分钟，worker 首次要下载 paddle + 模型，可能 10–25 分钟（已做镜像预热，只影响首次构建）。

### 12.3 那个容易漏的坑：云托管自己不提供域名备案

微信云托管官方文档原文：

> 「微信云托管主要面向小程序/公众号业务，一般情况下无需使用自定义域名，**因此暂未支持域名备案功能**。
> 当前推荐**另外购买服务器专门做备案之用（买最便宜的即可）**。」

也就是说：绑定自定义域名要求域名已备案，而备案需要备案服务号，云托管**不提供**备案服务号。
⇒ 如果你需要域名，就得**再买一台最便宜的云服务器**（轻量应用服务器约几十到一百元/年）专门用来拿备案服务号。
这笔钱很容易被漏掉。

**但有一条完全绕开的路**：官方同一文档开头即说明

> 「小程序/公众号前端调用云托管服务，**不需要使用域名**，请参考「访问云托管服务」，
> **不需要参考本文档进行自定义域名绑定，也不需要域名备案。**」

⇒ 小程序全部走 **CallContainer（云调用）** 时，域名、备案、那台备案专用服务器**全都不需要**。
代价是图片上传没有 uploadFile 等价物（见 §10.3），这是本项目要做技术决策的地方。

### 12.4 月成本估算（三种情形，均不含 PG/Redis）

| 情形 | 容器月费 | 适用 |
|---|---|---|
| **A. 当前架构**（worker 常驻，见 §7 警示） | api 0.5 核 1G ≈ **43.5** + worker 2 核 4G ≈ **173.7** = **≈217 元/月** | 内测与正式**都只能用这档**——worker 最小副本不能设 0 |
| **C. 砍掉 worker + Redis，api 同步跑 OCR** | api 2 核 4G ≈ **174 元/月** | 代码里已有「Celery 不可用 → 同步 OCR」的兜底路径（`app/routers/files.py`），把 api 服务改用 `Dockerfile.worker` 即可跑通；省一份容器费 + 整个 Redis 费，代价是上传变同步阻塞 |

**合计参考**：A ≈ 217 + PG(60–150) + Redis(30–80) + 存储(1–5) ≈ **310–450 元/月**；
C ≈ 174 + PG(60–150) + 存储(1–5) ≈ **235–330 元/月**。
前 12 天有免费额度抵扣，之后按上表。

> **更正（2026-10-18）**：本手册早先版本写过「内测期用 worker 最小副本设 0 最省」，
> **该建议已撤回**——官方明确 worker 这类「不接受 HTTP 请求」的服务会被自动扩缩容误判为
> 无使用而缩容，且扩容也由 HTTP 流量触发，可能导致 OCR 永久停摆。详见 §7 警示。
>
> **结论**：内测期没有「省掉 worker」这一档，要么按 A 常驻（容器 ≈217 元/月），要么按 C 砍掉 worker。
> 还想再省，可以把 api 压到 **0.25 核 0.5G、最小副本 0**（≈**22 元/月**）：api 是 HTTP 服务、
> 有真实流量，缩容到 0 后能被正常拉起，代价只是冷启动几秒。OCR 之外我们全是轻接口，值得先这么起步。

### 12.5 配置项真的有那么多个吗？——拆开看

`cloud-hosting.env.example` 里登记了 **22 项**，看着吓人，但按「现在要不要填」拆开是这样：

| 分类 | 数量 | 现在要填吗 |
|---|---|---|
| **平台硬需求**（库地址 / Redis / JWT / 微信 AppID+Secret / LLM Key） | 6 | **要，绕不开** |
| **对象存储**（COS 或 OSS，二选一） | 4 | 要（否则图片重启即丢） |
| **微信支付**（商户号 / APIv3 密钥 / 证书序列号 / 商户私钥 / 平台证书 / 回调地址 / mock 开关） | 7 | **一个都不用填**——本轮支付整体关闭，等转企业主体再说 |
| **有合理默认值**（`LLM_BASE_URL` / `SHARE_BASE_URL` / `ALLOW_DEV_LOGIN` / `PAYMENT_MOCK_ENABLED`） | 4 | 不填也能跑，只是用默认值 |
| **调优项**（`RUN_MIGRATIONS` / `UVICORN_WORKERS` / `CELERY_CONCURRENCY` / `CONTENT_SECURITY_ENABLED` / `CORS_ALLOW_ORIGINS`） | 5 | 清单里默认注释掉，不填 |

⇒ **实际要填的是 10 个左右，其中 6 个是任何后端都躲不掉的**（库、缓存、签名密钥、第三方凭据）。

### 12.6 复杂度来自哪里：不是代码量

实测代码规模（2026-10-18）：

| 部分 | 文件数 | 行数 |
|---|---|---|
| 后端 Python（`services/api/app` + `packages/core`） | 55 | 6,383 |
| 小程序 TS/TSX（`apps/miniapp/src`） | 27 | 3,186 |
| **合计** | **82** | **≈9,600** |

11 个路由、8 张表、api 侧 15 个依赖——这是一个**很小**的后端。让人觉得复杂，来源是三件事，全都不是代码量：

1. **异步 OCR**：Celery + Redis + 独立 worker 服务 ⇒ 多一个容器、一个采购项、一套配置。
   **这是唯一可以砍掉的**（见 §12.4 方案 C：api 同步跑 OCR，代码里已有兜底路径）。
2. **PaddleOCR**：模型 2GB+、推理吃 4GB 内存 ⇒ worker 规格降不下来。
3. **微信生态合规**：备案、域名、内容安全、隐私指引——这些是**法规和平台要求**，任何小程序项目都一样，
   不是我们的代码带来的。

另外要承认：**启动体检、内容安全、各种开关、preflight 是我们主动加的一层复杂度**，
换来的是「配置错了在部署阶段就炸，而不是上线后静默丢数据/被刷额度」。如果你觉得这层也可以省，
`CONTENT_SECURITY_ENABLED=false` + 不设 `APP_ENV=production` 就能全部绕开（但提审与生产风险相应上升）。

> 补充一句，避免走错路：**不要为了「简单」改用云开发（CloudBase 云函数）**。
> 早先评估已结论：PaddleOCR 模型 209MB 超出云函数部署包限制、Celery/Redis 在云开发里没有对应物、
> 关系型模型要改成文档型——那是「看起来简单、实际是重写」。对照见
> `cloudrun-migration-assessment/cloudrun-migration-assessment.html`。
